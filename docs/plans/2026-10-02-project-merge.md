# 项目合并（把项目拉下来当父任务）

> **这一份已经与最终实现对齐：正文说的是「做成了什么」，不是「当时打算做什么」。**
> 与获批稿不同的地方就地标出，编号对应文末的《获批之后的修订》。改动有三处，其中一处是**获批稿本身写错、被 check 脚本抓出来的实现顺序**。

## 背景

软件的设计宗旨是「项目 = 根目录，任务 = 文件/文件夹」（用户写在新手任务里的话）。缺的是**项目级别**的操作：项目之间此前没有任何往来，一个项目只能整体删掉，没法把它并进另一个。

要做的：勾若干个**要并走的项目**，把它们并进一个**并进到的项目**。两种形态当场选：

- **变成父任务**（默认）：每个被并走的项目在目标里变成一个同名任务（文件夹），它原来的顶层任务挂到它下面。
- **直接铺平**：那些顶层任务直接成为目标的顶层任务。

被并走的项目本身消失 —— 任务都搬走了，项目列表里不再有它。这是「合并」这个词的意思。

合并即「把根目录拖进另一个根目录」，它在文件管理器里不是新概念，是一次移动。所以这次**不加任何数据字段、不加新集合**：`Task.projectId` + `Task.parentId` 已经能表达全部结构。

## 屏幕上会变成什么样

**工具栏（`src/pages/GanttPage.tsx`）。** 那个「管理任务 / Organize」按钮改叫**「编辑模式」**，因为它从此不只管任务了。它右边那枚「编辑模式 / Editing」小字删掉：按钮自己已经写着这四个字、按下去还会高亮，再来一枚是重复。`gantt.manageTasks` 这个键三份字典里都删掉，按钮改用 `gantt.editMode`（zh 现值就是「编辑模式」，en 从 `Editing` 改成 `Edit mode`，fr 改成 `Mode édition`）。

**编辑模式下**，工具栏多一个**「项目管理」**按钮（`project.manage`，图标 `FolderInput`）〔改动 2〕。不在编辑模式时它不出现；工具栏被选择栏顶掉时（勾了任务行）也不出现 —— 和其它按钮一样。

**项目管理弹窗**（`src/components/ProjectManageDialog.tsx`）：

```
 项目管理                                          ✕
 ────────────────────────────────────────────────────
 要并走的项目
   ☑ ● 工作              12 项任务
   ☑ ● 生活               3 项任务
   ☐ ● 学习               5 项任务

 方式   ( 变成父任务 )  ( 直接铺平 )
 并进到  [ 学习 ▾ ]

 合并后 · 学习
   ├─ 需求评审
   ├─ 接口设计
   └─ 工作                      ← 新，画成强调色
      ├─ 周报
      └─ 复盘
 ────────────────────────────────────────────────────
                               [取消]   [合并]
```

- 源是一列复选框，目标是一个下拉，方式是 `Segmented`（`src/components/ui.tsx`，工具栏切日/周/月用的同一个）。**底部那张图才是重点**：按当前勾选和方式算出的「合并后长什么样」，画的是目标项目那棵树；切一下方式图立刻变，一层缩进还是一排平铺一眼能比。超长就滚动，不截断。
- **源那一列不是一个 `Field`**〔改动 3〕。`Field` 渲染的是 `<label>`，而这里一行一个标签、一列都是标签，外面再套一层 `<label>` 会把整列的点击都交给第一个复选框。
- **目标不可能同时是源**：选中哪个项目当目标，它就从源里被取消勾选；反过来，作为目标的那一行复选框是禁用的。所以「源 = 目标」这个非法状态到不了，按钮不需要解释自己为什么变灰 —— 它只是在没勾够时置灰。
- **没有叙述性文字，也没有二次确认。** 获批稿里有一行「源项目会被删掉，这一步不能撤销」，实现前就被用户去掉了（见《获批之后的修订》）：图本身就是后果说明。
- **不进撤销**。与 `deleteProject` 一致，理由更强：这一步**新建**了一个文件夹任务，而撤销记录只存「原来就有的行、它们的字段原来是什么」，它删不掉新建的行 —— 硬撤销会在目标项目里留下一个空壳文件夹。
- 新行（那个新建的文件夹）在图上画成强调色，其余画普通字色。这是形不是文案，符合「一个颜色一个含义」的老规矩。

## 数据与逻辑

### 纯函数 `mergeInto`（`src/lib/tree.ts`，新增导出）

```ts
mergeInto(
  tasks: Task[], projects: Project[],
  sourceIds: string[], targetId: string, asFolder: boolean,
  newId: (project: Project) => string,
): { tasks: Task[]; projects: Project[] } | null
```

放在 `placeTasks` 旁边。**store 动作和弹窗那张图调的是同一个函数** —— 图不会承诺一个按下去不会发生的结果（和拖拽预览共用 `placeTasks` 是同一个理由）。`newId` 是参数而不是内部调 `uid()`：纯函数里没有 `uid`，而预览也不需要真 id（弹窗传 `(p) => 'preview:' + p.id`）。返回 `null` 表示没什么可做，调用方什么都不做。

要点，按代码里的顺序：

1. **先算出每个被并走项目的顶层任务，再做任何改写。** 顶层列表只排除归档行（它们不挂到新文件夹下，见第 4 条），并且是在改写**之前**读的 —— 改写之后所有行都写着目标项目，再也没有信息说得出哪几行原来是它的顶层。
2. **先落位、后改 `projectId`**〔改动 1〕。`placeTasks` 的目的地列表取自「已经属于目标项目的行」；先改 `projectId` 的话，源自己的顶层行会被当成目标的原有行一起编号 —— 序号被撑大，而且它们会按旧比较器插进目标原有行中间。获批稿把这一步写反了，是 `scripts/check-project-merge.mjs` 抓出来的。
3. **只有两处真的需要 `placeTasks`**：
   - 铺平：`placeTasks(next, roots, null, null, targetId)` —— 插进目标顶层列表，整表重排序号（它同时负责给这些行改 `projectId`）。
   - 变成父任务：只为**新建的文件夹**调一次，拿它在目标顶层列表里的位置。源的行挂进这个文件夹时**不经过 `placeTasks`**：文件夹是新建的、孩子列表本来就是空的，没有兄弟列表要重排，直接改 `parentId` 反而保住了源项目原来那份顺序。
4. **归档的行跟着走，但不挂到新文件夹下。** 它们只被最后那一遍 `projectId` 改写覆盖，`parentId` 保持 `null`，于是成为目标项目的**归档根**，`archivedRoots` 照常收、恢复照常能用。理由是屏幕上什么都不会变（归档的行画在抽屉里，从不画在父任务下面），而且可能造出一个「活的文件夹、孩子全是归档的」这种看起来是空的行。
5. **位置放完之后的最后一遍**：把所有还写着被并走项目的行改成目标项目。这一遍接住两类行 —— 归档的顶层行（第 4 条，从没被 `placeTasks` 见过）和**孤行**（手改过的导入数据里 `parentId` 指向不存在的 id，从根往下走永远走不到它）。项目马上就要不存在了，还指着它的任务是一条没有项目线挂得住的行。
6. **一个可见顶层任务都没有就不建文件夹**（`roots.length === 0` 跳过）。空项目合并的实际效果就是删掉它。理由是同一天定下的两条规矩里的另一条：一个盖在空处、还得展开才知道是空的文件夹，是一行白说的话。（`buildRows` 的空项目规则后来反过来了 —— 空项目现在也画项目行 —— 但这条不跟着变，见 FEATURES 第 26 节。）只有归档任务的项目同理：不建文件夹，那些行仍然跟着走。
7. 重复名字不去重。项目重名本来就被允许（`addProject` 不查重），任务重名也是，id 不同就够了。

### store 动作（`src/store/useStore.ts`）

`mergeProjects(sourceIds, targetId, asFolder): void`，放在 `deleteProject` 旁边。实现就是调 `mergeInto(s.tasks, s.projects, …, () => uid())`，然后收尾：

- `projectFilter`：指向被并走的项目时改成 `targetId`，是 `'all'` 或指向幸存的项目时不动（比 `deleteProject` 一律归 `all` 更贴切）。
- `selectedProjectId`：指向被并走的项目时置 null。`selectedTaskId` 不动 —— 所有 id 都活着，打开着的任务面板仍然有效。
- **`lastUndo: null`**：合并前如果刚拖过一次，那条撤销记录会把 `projectId` 写回一个已经不存在的项目。
- `logs` **一条不动**。行都活着，日志当然活着 —— 和 `deleteProject` 正相反，那边任务没了。

`syncParentDates` / `effectiveStates` 不需要任何改动：新文件夹有活的孩子，下一次 App 的 effect 会照常把跨度写回它。

**一个不打算修的小损失**：被并走项目里顶层待办原本有自定义文件夹名（`todoFolders` 按 `todoGroupId` 存），合并后键变了，那个名字就丢了。为一个标签做迁移不值当，代码里留了注释。

### 那张效果图怎么画

弹窗里 `useMemo` 调 `mergeInto`，用 `buildChildrenMap`（既排序又只走一遍）拿结果里**目标项目的那棵子树**，递归渲染。归档行跳过：它们在看板上画在抽屉里，图把它们拉回父任务下面就是画了一棵应用从不画的树。不走 `buildRows` —— 那是整块看板的行（项目行、待办文件夹、归档抽屉都在里面），为了画一个项目再切一遍反而绕。

**画的是带连接线的谱系图，不是缩进列表**〔改动 5〕：每行带一条谱系线，祖先里还有后续的走一根竖线，每一级列表的最后一项走拐角、其余走分叉。理由是「深一层」和「这一支到头了」是两件事，只有后者能说出下一行是兄弟还是叔叔 —— 纯缩进把这两件事画成一样。这版走过三步：先是纯缩进不画线，被用户退回（计划正文那张草图本来就带线）；第二版按 `├─` / `└─` / `│` 拼字符串，字体里 `│` 填不满 24px 行高，竖线渲染成一节一节的短棍，正是谱系图最不能有的样子；第三版改成 **CSS 画的发丝线**，并且**把 `TaskTreeDialog` 里那段现成的绘制抽成 `ui.tsx` 的 `TreeRails` 两边共用** —— 应用里本来就已经有一张谱系图，没有理由再写第二张。「刚并进来的行」仍然画成强调色。

### i18n（`src/lib/i18n.ts`）

三份字典都加了（少一个 `tsc --noEmit` 就红）：`project.manage` / `mergeSources` / `mergeTarget` / `mergeMode` / `mergeModeFolder` / `mergeModeFlat` / `mergePreview` / `mergeConfirm`，外加把 `gantt.editMode` 的值改掉、删掉 `gantt.manageTasks`。复选框右边的任务数复用已有的 `common.taskCount`。

## 验证

1. `npm run build`（先跑 `tsc --noEmit`）通过。
2. `node scripts/check-project-merge.mjs` 通过。二十余条断言，覆盖：变成父任务（源项目消失、同名任务出现且为 phase、顶层任务挂进去、孙子也改了 `projectId`、目标顶层 `order` 连号且新文件夹在最后、`buildRows` 画得出来）、铺平（不新建任务、目标顶层按序增长）、归档分支（保持 `archivedAt` 与 `parentId: null`、进 `archivedRoots`、不建文件夹但仍搬走）、孤行、空项目、自己并自己/未知 id/空列表都是无操作、两个同名源产生两个文件夹、以及筛选/选中/撤销记录/日志的收尾。另有一条断言**预览和执行是同一块看板**：同一个输入连调两次、只换新任务的 id，结构逐字段相同。
3. **没有实际点过界面** —— 仓库里没有浏览器自动化，这一条只能人工验。
4. 顺带发现（与本次改动无关）：`scripts/check-archive.mjs` 在 HEAD 上就是红的。它写死了 2026-09-01～09-30 的任务窗口，而「进行中 / 已逾期」是拿今天比的，今天已过 09-30。把改动 stash 掉、在未改动的版本上跑，报错一模一样。

## 获批之后的修订

1. **获批稿把 `projectId` 改写写在了落位之前，是错的。** 获批稿第 2 步先「改写 `projectId` 时一并覆盖孤行」，第 4 步才调 `placeTasks`。而 `placeTasks` 的目的地列表正是从「已经属于目标项目的行」里取的，于是源自己的顶层行被算成目标的原有行：序号从 `[0,1,2]` 变成 `[0,2,4]`。改成先落位、最后统一改写。抓出来的是 `scripts/check-project-merge.mjs` 里那条 `order` 连号的断言 —— 这正是它存在的理由。
2. **工具栏按钮的图标定为 `FolderInput`**，获批稿没指定。编辑模式那个按钮已经用了 `FolderTree`，两个相邻的按钮不该共用一个文件夹图标。
3. **源项目那一列不用 `Field` 包**。`Field` 是 `<label>`，而这一列每行本身就是标签，套一层会让整列的点击落到第一个复选框上。改用与 `Field` 相同的标题样式、不套 label。
4. **去掉了「源项目会被删掉，这一步不能撤销」那行说明** —— 用户在批准后要求改成效果图，弹窗里不留叙述性文字。相应地，获批稿里的 `project.mergeSentence`（那条「将 X 以 Y 方式放在 Z 里」的整句）也没有实现：句子和说明一起被图取代了。
5. **效果图从缩进列表改成带连接线的谱系图，而且用了三轮。** 第一版只按层级缩进、不画线，用户看过之后指出「计划里那张带线的谱系图不是画得挺好吗」—— 计划正文里那张草图本来就带 `├─` / `└─` / `│`，实现时丢掉了。第二版按这些字符拼前缀，渲染出来竖线断成一节节的（字体里 `│` 的墨迹只有 1em 高，塞在 24px 行里必然留缝）。第三版改成 CSS 画的发丝线，并且**把 `TaskTreeDialog` 里那段早就写好的谱系绘制抽成 `ui.tsx` 的 `TreeRails`，两处共用** —— 应用里本来就有一张谱系图（第 22 节），再写第二张就是两个「分支长什么样」的答案。抽屉里那块没有 `font-mono` 之后的等宽对齐问题，字色仍是应用自己的字色，只有新建的行画成强调色。
6. **预览框从 `max-h-44` 抬到 `max-h-72`。** 七个行高之后就开始滚，两个源项目的合并会被切掉一半 —— 一张看不到第二个文件夹的图，画的是错的东西。
7. **补了一套开发预览页**：`preview-merge.html` + `src/dev/merge-preview.tsx`，照 `preview-update.html` 那套写（不启 Tauri、不碰真数据，`vite build` 只吃 `index.html` 所以进不了安装包）。`?mode=flat` 看另一种形态、`?lang=` / `?theme=` 看其它语言和配色。两个源项目和方式都是挂载后用轮询点上去的，和 `update-preview.tsx` 里 `?open` 的做法一样。
8. **用户看过第一版渲染之后的三处改动**，都在同一轮：
   - **独子少一根线。** 用户指出「被移动的项目和其子任务之间少根线」。根因在 `TreeRails`：`first && !below`（既没有上一个也没有下一个兄弟，也就是独子）四根线一根都不画，只剩一截横杠，那一行像凭空掉下来的。改成和「同级的最后一个」一样画 `└`，因为「上面只有父任务」正是那个拐角要说的话。**这条修的是共用件，第 22 节那张谱系图一起吃到了。**
   - **目标项目也进图**，原来是图上面一行 `合并后 · 工作` 的说明。它是下面所有东西被放进去的容器，漏掉它这张图没法对着看板读；它下面的一切因此整体多缩进一级。`project.mergePreview` 的 `{name}` 占位符随之去掉。
   - **并进来的那几块套虚线框。** 边框包在每段最外层，不逐行加 `border-l` —— 逐行画的话虚线每 24 像素重新起头，读起来是点线。框住一整块（文件夹模式 = 新文件夹及其整棵子树，铺平模式 = 该项目原来的顶层那一段），相邻来源各一个框。为此预览从**平铺数组改成了嵌套结构**：一个子树没法在平铺列表里框出来，除非去量它在屏幕上的起止。
   - **框的颜色改成该项目自己的颜色**（追加）：第一版是强调蓝，用户要求跟项目色一致 —— 那样框说的是「哪**个**项目进来了」，和它在勾选列表里的圆点、在甘特图里那条项目线是同一个颜色。颜色来自数据不是主题，所以用 `color-mix(… 50%, transparent)` 调淡，Tailwind 的 `/40` 后缀只对主题颜色变量生效。
   - **`inside` 参数防嵌套框。** 第一版按「每个同源段一个框」实现，结果一个项目的行在它自己**每一层**都是同源段，画出三层框套同一个子树 —— 渲染出来才发现。只有来源与当前所在框**不同**的段才开新框。
9. **预览框从 `max-h-72` 再抬到 `max-h-96`。** `max-h-72` 在验证用的那份数据上仍然截在第二个源项目之前 —— 一张看不到最后进来的东西的图，画的是错的东西。
10. **无头截图的两个坑，记下来免得下次再查。** 一是 `--run-all-compositor-stages-before-draw` 不能省：不加时截出来的图里，被点过的那个分段控件停在上一帧的颜色上，和同一张图里的树自相矛盾（`--dump-dom` 证明 DOM 是对的，纯粹是合成器没重画）。二是预览页的轮询**一轮只点一样**：三个 `click()` 挤在同一轮里，React 对离散事件逐个 flush，截图会落在两次之间。
