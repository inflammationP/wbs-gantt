# 项目色扩容与更新对话框的「历史版本」

> **这一份已经与最终实现对齐：正文说的是「做成了什么」，不是「当时打算做什么」。**
> 与获批稿不同的地方就地标出，编号对应文末的《获批之后的修订》。改动有三处，其中一处是用户在批准时直接改的（版本号定为 v0.12.0），一处是用户砍掉的（不做真流程的手工验证）。

## 背景

两件互不相干的小事，凑在一起是因为都小、都在同一个 release 里。

**项目色不够用。** `PROJECT_COLORS` 八个颜色，而颜色在这个应用里是**项目的身份**（状态另有一套信号色，两套不能混 —— 见 FEATURES §13 与 `gantt.` 那一组）。建到第九个项目，新建的那个只能和已有的撞色，撞了就等于没有身份。

**跳过的版本读不到。** 更新对话框只有一份说明，取自 `latest.json` 的 `notes`，也就是**目标版本**那一份。从 0.9.0 直接升到 0.11.0 的人永远不知道 0.10.0 改了什么 —— 中间那些版本的说明只存在于 GitHub Release 页面上，而会去翻那个页面的人不会卡在更新对话框里。仓库这边的材料一直是齐的：`release.mjs` 每次发布都把同一段文字同时写进 Release 正文和 `latest.json`，缺的只是展示。

## 屏幕上会变成什么样

**项目对话框里的色板**从两行八格变成两行十二格〔改动 1〕。原来的八个一个不动、一个不换位，新的四个（红、青、黄绿、品红）接在后面 —— 新建项目按「这是第几个项目」取色，重排会把所有人屏幕上的默认色一起换掉。已经建好的项目存着自己的色值，不受影响。

**更新对话框**，本次说明那个框下面多一行小字：「本次将连带更新的历史版本内容（3 个版本）」。默认收起，点一下才展开；展开后一个版本一段，版号加粗、下面跟着那次发布写的说明，和上面那份一样按纯文本换行。**只有真的跳过了版本才会出现** —— 相邻版本升级的人看到的对话框和以前一字不差。

**它拉得回来才出现。** 没有加载中的转圈、也没有「获取失败」的红字：拉的时候不出现，拉不到也什么都不出现，两者样子一样。理由是这个列表是整次更新检查里**唯一**不影响「更新能不能装上」的部分 —— 连不上 GitHub 的人本来就有一条「自动更新不可用」的横幅，为一份可看可不看的内容再报一次错只是噪音。

**改这个弹窗的人不用先发一次版。** `npm run dev` 打开 `http://localhost:1420/preview-update.html`，就是真实的对话框配一组写死的假数据：一个假的新版本、两个假的旧版本。`?lang=fr`、`?theme=paper` 看另外两种语言和另外三套配色。

## 怎么做的

**调色板**（`src/lib/ui.ts`）：末尾追加四个十六进制值，注释里写清「只追加、不重排」和它的理由。

**版本比较与筛选**（`src/lib/updater.ts`）：`releasesBetween(releases, current, target)` 纯函数，留下**严格大于 current、严格小于 target** 的条目、按新到旧排序。逐段取数字比较，不是字符串 —— `'0.9.0' > '0.10.0'` 按字符串比会把新的那条当成旧的丢掉，而整个 0.x 线都是这个形状。

**拉取**（同文件）：`fetchReleaseHistory` 走 `api.github.com` 的 Releases 接口，读 `tag_name` / `body`（`body` 就是发布时写的那份说明），顺手把 tag 上的 `v` 去掉，好让组件直接画 `v{version}`。写法照抄 `src/lib/notify.ts`：懒加载 `@tauri-apps/plugin-http` 的 `fetch`，带 `connectTimeout`，非 Tauri 环境直接返回空。结果缓存在模块级变量里，一次运行只请求一次；**只在成功解析后才写缓存**，所以失败会重试而不是被记住。

**失败一律返回空数组**，不抛错、不提示。原因是上面那条：它不影响能不能装。

**列表进 store**（`src/store/useStore.ts`）：`updateHistory: ReleaseNotes[]`。弹窗展示的另三样（`updateInfo` / `updatePhase` / `updateError`）本来就在 store，这是第四样；组件因此不持有任何状态。`runUpdateCheck` 里这次拉取**在对话框已经弹出之后**才发 —— 版本号、说明、安装按钮都不等它；被「不再提醒」静默掉的那次不拉（没人看着对话框）；开查时先清空 —— 否则换个目标版本重查、而新的历史还没回来时，旧那几版会暂时挂在新的更新说明下面。

**折叠**（`src/components/UpdateOverlays.tsx`）：原生 `<details>` / `<summary>`，开合状态是平台的，React 里没有可存的东西，也没有新增组件。列表为空就整个区块不渲染 —— `releasesBetween` 返回空正好就是「没跳过版本」，函数与界面因此天然一致。

**capability**（`src-tauri/capabilities/default.json`）：http 插件的 allow 里加一条 `https://api.github.com/*`。Tauri v2 的 ACL 默认拒绝一切插件命令，漏掉不构建失败、只静默拒绝（FEATURES §17 记过这条）。

**预览页**（`preview-update.html` + `src/dev/update-preview.tsx`）：入口 HTML 在根目录，模块只做三件事 —— 把假的 `updateInfo` / `updateHistory` 塞进 store、按 URL 参数设置语言与主题、挂上 `<UpdateOverlays/>`。语言和主题走 `applyLang` / `applyTheme` 而不是 store 的 `set*`（后者落盘，看一眼对话框不该改掉下次打开应用时的语言）。**不进安装包**：没有任何地方 import 它，`vite build` 也只打 `index.html`（`vite.config.ts` 没有第二个 `rollupOptions.input`，`dist/` 里只有一个 html）。和 `scripts/demo-seed.mjs` 是同一种东西。

## 验证

- `scripts/check-update-history.mjs`（新增）：`v` 前缀、前后两端都不算、只差相邻一版时返回空、乱序输入要新到旧、`'0.9.0' > '0.10.0'` 这条字符串比较会答错、以及版本段数不同时缺失的尾段读作零。
- `npm run build`：`tsc --noEmit` 先跑，字典缺键（`update.history` 三份都要有）在这一步挡住。
- 预览页手工看：折叠、展开、长说明会不会撑破弹窗、三种语言、四套主题。
- 〔改动 3〕**真流程没有手工走**（用户选择只留预览页）：临时把 `tauri.conf.json` 降到 0.9.0、`npm run tauri dev`、还得连得上 GitHub，三条加起来不值当。所以「从 GitHub 拉回正文」那一趟**没有实测**，实测的是它拿回数据之后的筛选、排序与渲染。

## 获批之后的修订

1. **版本号由用户定为 v0.12.0**（获批稿里写的是备选，按仓库规矩版本号是用户的决定），`tauri.conf.json` 与 CHANGELOG 一节同时落到 0.12.0。日期落在 **2026-10-01** —— 计划是 09-30 晚上批的，跨了零点，文件名与 CHANGELOG 抬头都按写完那天算。
2. **`v` 前缀的剥离从 `releasesBetween` 挪到了 `fetchReleaseHistory` 的解析里。** 获批稿把两件事都说成这一个函数的责任；实现时想清楚：筛选与排序只需要**比较**时容忍前缀，而返回的字符串要能直接画出来。于是纯函数保持「进什么出什么」，规范化留在唯一的数据入口。check 脚本相应钉的是「带前缀也能正确比较」（`scripts/check-update-history.mjs` 里那条断言，期望值保留 `v`）。
3. **真流程的手工验证按用户要求砍掉**，只留预览页 —— 用户对这个弹窗的验收方式是「能打开预览页看到它」，不是「走一遍真升级」。代价记在上面验证一节里。
