# 历史操作树（分叉、多步撤回）

> **这一份已经与最终实现对齐：正文说的是「做成了什么」，不是「当时打算做什么」。**
> 与获批稿不同的地方就地标出，编号对应文末的《获批之后的修订》。改动有六处，其中**两处是实现过程中被工具抓出来的**（一处被 check 抓出、一处被渲染抓出），还有一处推翻了获批稿的核心呈现方式。

## 背景

原来只有**一步**撤销：`UndoStep` 存「原来就有的行、它们的字段原来是什么」，10 秒后自动消失，而且只在甘特图页面生效。合并一个项目会一次性动几十项任务，撤错了只能靠手往回搬 —— 这就是这一节要做的事的直接起因。

做成的是一棵**历史操作树**：编辑模式工具栏上、`项目管理` 旁边一个入口，记录本次打开以来的所有结构性操作，点任意节点一次退/进很多步，不在生效路径上的画灰。分叉保留，关掉软件即消失。

## 一个先说的结论：SW 那种「找不到参考」不会发生

起因里有他的一句话担忧：像 SolidWorks 里删掉实体会让下游特征找不到基准面那样，撤回会不会因为前置依赖而失败。

**按步走的模型里这个前提不成立。** 跳转永远是从当前节点**沿树走到**目标节点：向上的各路步骤施加逆、向下的施加正，严格按它们当初被施加的顺序。路径上每一步的前置状态都是前一步重建出来的，所以「把 X 挂到 Y 下面」必然找得到 X —— 创建 X 的那一步在同一条路径上，且先被重放。

会出问题的是**整块快照覆盖**：它会把**没记进历史的东西**一起冲掉（合并之后写的三篇日志，撤回合并时会被快照吃掉）。所以本设计不用快照，用可逆增量。

代价写在另一处，而且是硬的：**一旦有结构性改动漏掉记录，这个保证就没了**。所以记录方式跟着改了。

## 记录方式：store 自己看着自己

`withUndo` 原来由二十个 UI 调用点手工调用，这正是「移出到顶层」（`setTaskParent(id, null)`）和「待办文件夹改名」从来没进过撤销的原因：漏掉一个不报错，只是那个操作永远撤不回来。

改成 `useStore.subscribe` 里比对 `tasks` / `projects` / `logs` / `todoFolders` 的身份，变了就算增量入栈。**忘了贴标签的那一步照样会被记下**，只是名字由增量自己拼（`history.autoAdd` / `autoRemove` / `autoChange`）—— 失败模式从「静默丢失」变成「不好看」，而「不好看」是可以修的，「丢失」不是。

`withUndo(message, run, scope?)` 保留下来只负责三件事：起名字、把一次手势里的多次 `set` 合成一步（可重入，嵌套时外层胜出）、标 `scope: 'project'`。二十个调用点一个字没改。

三类写入被挡住：`syncParentDates`（派生写入，每步都会拖一条噪声跟在后面）、回退/前进自己施加增量的那一次 `set`、以及 `importData`（整体换掉看板，历史同时清空；不清的话清空的那一步会立刻被记进刚清空的树里）。

`activeView !== 'gantt'` 那道闸门**删掉** —— 他明确说非编辑模式下的结构性操作也要记。条纹还是甘特图的，历史是看板的。

## 增量的形状（`src/lib/history.ts`）

一步 = 它碰过的行，不是整块看板：

- `changed`：前后值各一份，**外加那一刻的名字**。名字单独存是为了展开时不必回当前看板查 —— 灰掉岔路上的那一步指向的行可能已经没了；顺带显示的是**那一刻**的名字，和已经记死的整句标签同一套口径。
- `added` / `removed`：整行。有了它们，一个**创建**了行的步骤（新建任务、合并产生的文件夹、新建项目）才撤得掉 —— 上一轮做项目合并时回答「为什么不能撤销」，给的就是这条路缺了半截。
- `removedLogs`：随行一起没掉的日志。**日志只以这一种方式进历史**：写、改、删日志本身是内容，不进；但撤销一个删除必须把日志一起放回来。
- `projects`：新增 / 删除 / 改过，同样前后各一份。

## 跳转

`historyGoTo(nodeId)`：从当前节点向上找到与目标的最近公共祖先，记下要逆着走的步骤；再从公共祖先向下到目标，记下要顺着走的。**把整条路径折完，再一次 `set`** —— 存盘订阅器在每次 identity 变化时全量 `JSON.stringify` 且没有防抖，五十步就是五十次全量序列化。

收尾和 `deleteTask` 同一套：`selectedTaskId` / `selectedProjectId` 指向已经不存在的行就置 null，`projectFilter` 指向没了的项目就归 `all`。

**找不到的行跳过，不报错** —— 按上面的论证这应该到不了，`if (!row) continue` 是一行护栏而不是功能。**不做「这步无法撤回」的提示界面**：构造不出能到达的场景，为一个到不了的场景写界面就是写没人读的代码。

## 界面上长什么样

**入口**：编辑模式的工具栏上、`项目管理` 旁边一个 `历史`。不在编辑模式时不出现，但历史照常在长。

**树从下往上长**：根（`history.now`「本次打开」）在最下面，越新的越靠上。容器 `flex flex-col-reverse` 把行序翻过来 —— DOM 顺序不变，所以按行算的那些量不用改。

**一列代表一个分支，不是一层。** 这一条见《获批之后的修订》第 1 条，它是**渲染出来才发现**的，也是本次唯一推翻获批稿呈现方式的地方。每行列宽固定成一整棵树的宽度，标签才不会参差；每一列从**分叉那一行**画起，不是从它自己的第一行。

**节点可以再展开**，列出这一步具体动了谁（新增 / 删除 / 改动 / 项目各一行，一行最多 20 个名字，多的用 `history.more` 收尾）。**展开和跳转是两个控件**：行本身点了跳转，行尾的小三角只摊开。

**项目管理弹窗最底部**另有一段可展开的 `history.projectHeading`，只列项目层面的步骤，按时间倒序，**不是树** —— 筛掉别的步骤之后树是断的，硬画会骗人。那一段是标题不是按钮。点一行跳转并关掉弹窗（底下的看板就要变成另一块看板了，一个按旧看板勾好的表单描述的是错的东西）。

## 获批之后的修订

1. **连线从「按层级」改成「按分支」。** 获批稿写的是复用 `TreeRails`、把竖向几段 `top`/`bottom` 对调（`flip`）就够。渲染出来才发现：历史上每一步都是从上一步做出来的，按层级缩进会把一条五十步的链画成一条往右下跑的阶梯，正好是树要解决的事。改成「第一个孩子接着父任务的列，往后的孩子各占一个新列」，链是一条直线，只有分叉才横向移动。`TreeRails` 的 `flip` 随之退回（没有调用方了，不留死代码），`HistoryDialog` 自己画一份约三十行的 gutter。
   - 配套两处也是渲染逼出来的：每行列宽必须**固定成一整棵树的宽度**（否则叉口那一行的标签会被推右边、名字参差，而且叉口的横线只能压在文字上）；每一列必须先**从分叉那一行画起**（否则分支的节点在叉口上面好几行时，叉口的拐角指向空气）。
2. **`todoFolders` 加进被捕获的看板。** 获批稿的操作清单里列了「待办文件夹改名」，但没说机制 —— 而它写的是 `todoFolders`，不在原来捕获的三个集合里，照原样实现会**静默漏掉**，正是这套设计要消灭的东西。加了 `HistoryDelta.folders` 一栏。
3. **i18n 用整句而不是前缀。** 获批稿列的是 `history.move` / `history.delete` 这类前缀，实现时发现那二十个调用点传进来的本来就是 `gantt.undo*` 那批整句，历史直接沿用即可；只有新接进来的操作需要新句子（`history.newTask` / `editTask` / `newProject` / `editProject` / `deleteProject` / `merge` / `outdent` / `folderRename`）。少了一层拼接，也少了一处会和现有句子不一致的地方。
4. **`deleteTask` 的身份修复。** 它给每一条没被删的任务重建对象（`dependencies` 过滤后总是新数组），在「身份即差异」的历史里，删一条任务会变成一条「改动了其余全部」的步骤，增量和步数都炸。改成没变就原样返回 —— 这条本来就是仓库存货的约定（旧 `withUndo` 的注释里写着），它自己没遵守。**是 `check-history.mjs` 里那条 `deltaCount === 1` 抓到的。**
5. **三个既有 check 跟着改。** `check-archive` 断言过 `lastUndo.patches`、`check-task-tree` 断言过「不在甘特图就不记」和「撤销不会复活一个已删除的任务」、`check-project-merge` 断言过「合并会清掉之前的撤销记录」—— 三条测的都是旧机制的行为。都改写成对新机制下**同一意图**的断言（前者改成查增量里前后都有 `archivedAt`；中者改成「不在甘特图也记」，以及「删除自己那一步的撤销确实会复活，只是移动的撤销不该」；后者改成「合并是一步，一次按下去源项目回来」）。
6. **新接进来的操作自己贴标签**：`addTask` / `updateTask` / `setTaskParent`（顶层时用 `history.outdent`）/ `setTodoFolderName` / 四个项目动作。这样二十个既有调用点一个字不用动，而新操作不至于都叫「改动 1 项」。
