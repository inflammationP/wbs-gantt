# 设置页「版本 / 更新」区块

> 归档自 `~/.claude/plans/breezy-stargazing-firefly.md`，内容为获批那一刻的方案。
> 实现过程中的偏离见文末「八、获批之后的修订」。

## 一、缘起

本项目的桌面端内置了 Tauri 自动更新，而此前发过的 11 个版本（v0.1.0 – v0.3.2）**全部静默失效**：capability 里只授予了 `core:default`，更新器的 IPC 命令被 ACL 拒绝；同时 `release.mjs` 用本地文件名（含空格）拼下载地址，而 GitHub 上传时会把空格改写成点，导致每个版本的安装包 URL 都返回 404。两处都在同一次会话的前半段修掉了。

修完之后的直接后果是：**更新失败仍然是无声的**。`src/lib/updater.ts` 的 `catch` 把一切降级成 `console.warn`，用户和作者都无从知道卡在哪一步。

所以这次要做的不是「加一个更新按钮」，而是**把不可见的更新过程变成可见的**：

1. 让用户能自己发起检查，不必等下次重启；
2. 连不上 GitHub 时明确说出来，而不是假装无事发生；
3. 长期连不上时主动提醒一次，推动用户去解决；
4. 顺手给出解决连接问题的手段和理由。

对一个国内用户为主的工具，「能否连上 GitHub」就是自动更新唯一真正的前提，而这一步此前完全黑盒。

## 二、获批的决策

| 决策 | 选择 |
|---|---|
| 长期未更新的提醒形态 | **启动时模态弹窗** |
| 已连不上 GitHub 时是否还弹 | **照常弹**（两者目的不同：横幅说「现在连不上」，弹窗推动去解决） |
| 手动检查发现新版本 | **先问再装**，并在同一弹窗内显示该版本的更新说明 |
| 提醒频率 | 暂定 30 天一次 |

## 三、现状（探索结论）

- 设置是**整页**不是弹窗：`src/pages/SettingsPage.tsx`，每个区块是裸 `<section>` + `<h2>` + 可选提示 `<p>`。
- 设置图标在 `src/components/Sidebar.tsx` 的导航按钮里，`NAV` 表在模块作用域。**全应用没有任何红点/徽标先例**，这是第一个。
- **前端完全没有版本号来源**：`package.json` 是陈旧的 `0.1.0`，真值在 `src-tauri/tauri.conf.json`，`vite.config.ts` 没有 `define`。
- **应用无法打开外链**：`src/` 里 0 个 `<a>`/`href`/`window.open`，两个平台都没装 opener/shell 插件。
- `Update` 暴露 `version` / `body`（即 latest.json 的 `notes`）/ `download()` / `install()`；`check()` 无更新时返回 `null`。**更新说明的链路是现成的** —— `release.mjs` 早已把交互输入的 notes 写进 latest.json。

### 两个必须避开的陷阱

1. `useStore.ts` 的 `persistPrefs()` 是**显式解构**的，新增 prefs 字段不写进去，就会在用户每次切换主题或语言时被抹掉。
2. `storage.ts` 的 `loadPrefs()` 是**逐字段重建**的（非展开），新字段不加进去会在每次重载时丢失。

## 四、方案

### 版本号
`vite.config.ts` 加 `define: { __APP_VERSION__: JSON.stringify(<tauri.conf.json 的 version>) }`，在 `src/vite-env.d.ts` 声明。选它而不是 `getVersion()`：`@tauri-apps/api` 只是传递依赖，且 Web 版拿不到值；define 一次覆盖两种构建，零新依赖。**`package.json` 的版本号不参与**。

### `updater.ts` 重写为纯函数
返回判别联合 `unsupported | current | available | error`。关键点：不自动安装，把 `Update` 资源包在返回的 `install` 闭包里；未安装路径要 `close()`（原代码漏了）；`error` 分支不再吞异常 —— 它就是「连不上 GitHub」的信号。

### store 动作
新增 `runUpdateCheck(mode: 'auto' | 'manual')`，包住 `runUpdateCheck()` 并记录结果。成功则把 `lastUpdateContact` 前移并清掉离线态；失败则置 `updateOffline`。新增会话态 `updatePhase` / `updateMode` / `updateInfo` / `updateInstalling` / `updateError` / `nagOpen`，以及三个持久化 prefs 字段：`updateNoticeDismissed`、`lastUpdateContact`、`lastUpdateNag`。

### 30 天提醒
首次 hydrate 时若 `lastUpdateContact` 为空，就用当下补写并落盘，保证新装用户不会第一天被骚扰。触发条件：`now - lastContact > 30d` 且 `now - lastNag > 30d`。弹过即写 `lastNag`。按用户决定，**不因离线而抑制**。Web 构建下该时间戳永不自增，因此提醒**只在桌面端启用**。

### 挂载点
启动检查改由 store 动作承载；提醒弹窗新建组件，挂在 `App.tsx` 里紧挨 `<GettingStarted />`；「发现新版本」弹窗用局部 `Modal`（`useDialogs().ask` 承载不了富内容）。

### 外链（需新增依赖）
加 `tauri-plugin-opener`（Rust + npm + 一条 capability），`src/lib/openUrl.ts` 分平台。替代方案（webview 内开新窗口）对本场景不可行：要链到的是一个**下载页**，webview 里的下载行为不可靠且没有地址栏。

### 平台差异
| 元素 | 桌面 | Web |
|---|---|---|
| 版本号 | 显示 | 显示 |
| 检查更新按钮 | 显示 | 不显示，改显示说明文案 |
| 连不上提示 + 红点 | 显示 | 不显示 |
| 30 天提醒 | 启用 | 不启用 |
| GitHub / Watt Toolkit 介绍块 | 显示 | 显示 |

## 六、链接核查

- `https://steampp.net/` → HTTP 200，`<title>Watt Toolkit</title>`，页面含 "Steam++" 旧名
- `https://steampp.net/download` → HTTP 200
- 交叉验证：官方仓库 `BeyondDimension/SteamTools`（26.8k stars、GPL-3.0、未归档）声明的 homepage 正是 `https://steampp.net`
- **技术可行性已确认**：更新器依赖树里有 `rustls-platform-verifier`，走 Windows 系统证书库校验，所以 Watt Toolkit 的自签根证书**会被信任** —— 它是帮忙而不是帮倒忙。（若它走 webpki 内置根证书，这条建议反而会把更新搞坏。）

## 七、验证方式

1. `npm run build` —— `tsc --noEmit` 强制三份 i18n 字典对齐。
2. `npm run tauri build -- --no-bundle` —— 验证插件注册、Cargo 依赖、capability 能编译。
3. 把 endpoint 改成不存在的主机，确认横幅 + 红点出现，点「我知道了」后重启不再出现。
4. 把 `wbs-gantt.prefs` 里的时间戳改成 40 天前，确认提醒弹窗出现；改成 1 天前，确认不弹。
5. 外链在 dev 下确认打开系统浏览器。
6. 真端到端需要发一版。

## 八、获批之后的修订

获批后先让一个 Plan agent 复核，采纳了以下修正；第 11 条则是实现过程中实测才发现的（**计划正文未及反映，以本节为准**）：

1. **`persistPrefs` 陷阱其实不是静默的。** `savePrefs(prefs: Prefs)` 要求完整类型，`loadPrefs(): Prefs` 又按该类型返回字面量，所以只要新字段声明为**必填**，漏改任何一处都是硬 `tsc` 报错。计划里把它写成「静默抹掉」过于悲观；正确做法是把三个字段全部声明为必填（可空的用 `string | null`，不用 `?`），让编译器兜底。

2. **30 天节流在「显示时」写入，不是关闭时。** 计划里写的是「弹过即写」，但没写清楚时机。若在关闭时写，用户在弹窗开着时强杀进程就永远不会关闭它，于是每次启动都被弹。已在代码注释里写明原因。

3. **`check()` 必须传 `timeout`。** 原实现没有超时；网络被墙时请求可能挂很久，横幅出现的时机不可预测。定为 15 秒。

4. **提醒的判定挪到「自动检查失败之后」执行**，而不是在挂载时独立判定。这样两条要求在构造上自然成立：检查成功已经把锚点推到当下，条件必为假；而连不上的人锚点始终陈旧，所以即使横幅已经解释了原因，弹窗照样会出现。

5. **新增一个 `import.meta.env.PROD` 门禁**，让 `tauri dev` 不会把已发布的正式版静默装到开发树上。开发环境与打包版共用同一个 endpoint，这是真实存在的坑。

6. **红点/横幅的判定不按 `updateMode` 过滤。** 计划里是用 `updateMode === 'auto'` 判定的，但那会导致「离线时点一下检查更新，横幅和红点当场消失」。改成只看 `updatePhase === 'unreachable'`：横幅说的是「自动更新不可用」，这句话在手动检查失败时同样成立，两者并存不矛盾。

7. **`diffDays` 不能配 `toDate` 使用。** `toDate` 按 `-` 切分并期望 `yyyy-MM-dd`，喂给它完整的 ISO 时刻会得到 `NaN`，被 `|| 1` 兜成**当月 1 号** —— 一个静默的错误日期。必须传 `new Date(iso)`。计划里没提这一条，是复核阶段读 `dates.ts` 时读出来的。

8. **外链渲染成按钮而不是 `<a href>`。** `<a>` 在 Tauri webview 里不会交给系统浏览器，会静默失败 —— 而「静默失败」正是这套链接要消除的东西，所以直接不用它。

9. **i18n 键从计划的约 24 个定为 25 个**（合并了重复的「以后再说」，补上了 `noNotes` / `installing` / `installFailed` / `webNote`）。

10. **文件命名与计划的差异**：`src/lib/appVersion.ts` 未创建（版本号只有一处使用，不必再包一层）；`src/lib/openUrl.ts` 命名为 `src/lib/links.ts`，因为它同时导出两个 URL 常量。

11. **版本号注入不能用 `define`，计划里的这一步是错的。** 计划（第四节「版本号」）写的是「`vite.config.ts` 加 `define: { __APP_VERSION__: … }`」。实现后生产构建确实正常，但拉下 dev server 的转译产物一看，`__APP_VERSION__` **原封不动留在代码里** —— 渲染设置页时会当场抛 `ReferenceError`。查 Vite 源码确认：define 插件对客户端模块在非构建时直接提前返回（`config.js` 里 `if (this.environment.config.consumer === "client" && !isBuild) return;`），**`define` 只在构建时生效**。

    改用 Vite 的 env 通道：在 `vite.config.ts` 里 `process.env.VITE_APP_VERSION = appVersion`，代码里读 `import.meta.env.VITE_APP_VERSION`。`loadEnv` 会主动收集带前缀的进程环境变量，而配置文件又先于它求值，所以两种模式都能拿到。**dev 与生产双模式实测过**：dev 下注入为 `"0.3.2"`，生产包里内联成字面量。

    这个坑值得单独记一笔，因为它**不会在构建时暴露** —— 只有把 dev server 真的跑起来渲染那个组件才会炸。若照计划直接交付，用户打开设置页就是一片白。

12. **「我知道了」永久关闭被用户推翻 —— 实现之后的需求变更。** 计划第二节把「设置一个『我知道了』按钮永久关闭该提示」列为获批决策，本节第 6 条还专门论证过判定不该按 `updateMode` 过滤。用户在看到实现后提出三点改动：

    - **红色提示每次检测失败都要出现**，不论这次检测是启动时自动发起的还是用户手动点的，**取消永久关闭**；
    - 删掉版本行里那行灰色的「无法连接到 GitHub。」（失败改由红框单独承担）；
    - **启动时的自动检查要显示和手动检查一样的回执**，即右侧的「已是最新版本。」。

    落地：删掉 `updateNoticeDismissed` 这个 prefs 字段（连同 `dismissUpdateNotice` 动作、`updateMode` 状态，以及 `update.dismiss` / `update.checkFailed` 两个 i18n 键）；横幅判定简化为 `updatePhase === 'unreachable'`；结果文案不再按 `updateMode` 过滤，因此那个状态字段整体移除。**注意启动时的自动更新行为没变**，仍是静默安装并重启 —— 变的只是它把结果报到界面上。

    **这次反转是有道理的，值得记下原因**：横幅陈述的是一个**持续成立的状态**（连不上 GitHub），而不是投递一条一次性通知。所以「关闭一次就永不再提」在语义上本来就站不住 —— 关掉之后状态依然成立，界面却在说谎。第 6 条当时的论证方向是对的（不该按 mode 过滤），只是没走到底。`FEATURES.md` 第 17 节已写明**不要**给它加回关闭按钮。

    **时间线上的一个重要事实**：本节前 11 条的成果（含那个「我知道了」永久关闭）**已经作为 v0.3.3 发布出去了**（`cec6c40` + 版本号提交 `38c49c9`，Release 页上可见）。所以第 12 条这次反转**属于下一个版本（v0.3.4）**，`CHANGELOG.md` 里单开了一节，没有去改已发布那节的内容 —— 唯一动过 v0.3.3 段落的地方，是订正本节第 11 条那处机制描述的事实错误（原文写的是 `define`，而实际发布出去的是 `import.meta.env` 通道），`v0.3.4` 那节的「修复」里有记。

    顺带记一笔：**v0.3.3 的安装包 URL 实测返回 HTTP 200**（`WBS.Gantt_0.3.3_x64-setup.exe`，点号名）。这是 `release.mjs` 那个「用 GitHub 回报的资源名拼 URL」修复的端到端证明 —— 修复前每一个版本的同类 URL 都是 404。

13. **启动时的静默安装也被推翻了 —— 又一处需求变更。** 本节第 12 条末尾特意写明「启动时的自动更新行为没变，仍是静默安装并重启」，用户随后直接否掉了这一点：**不管怎么检测，都是先问再装。** 启动时那次检查发现新版本，现在同样弹对话框，不再静默安装。

    落地：删掉 `runUpdateCheck` 里的自动安装分支（`available` 一律 `set({ updateInfo: result })`），并连带删掉本节第 5 条加的那个 `import.meta.env.PROD` 门禁 —— 它存在的唯一目的是阻止 dev 静默安装，没有静默安装就不需要了。

    注意第 5 条那个门禁**思路本身没错**，只是被取代了：它防的是「不做任何询问就把正式版装到开发树上」，而现在这一点由对话框本身保证 —— 用户看得见，点了才装。计划当初担心「每次启动都弹窗会把用户困在旧版本上」，用户的权衡是**打扰可以接受，静默重启不行**。因此启动时每次都会问一次，直到更新被装掉 —— 这是刻意的。

14. **两处后续变更，都出自同一句用户原话：「所谓自动检测就是开机的时候软件自己按了一下手动检测，所以最后的提示都应该是一样的。」**

    - **`mode` 参数整个删除。** 此前 `runUpdateCheck(mode)` 里唯一剩下的「按来源分支」是 `if (mode === 'auto') maybeNag()`，也就是自动路径才会弹 30 天提醒 —— 那是用户唯一还能看出来的区别。现在函数不接受参数，`maybeNag` 改为**任何**失败检测之后都评估。
      - 这不只是更一致，而是**更正确**：提醒陈述的是锚点的事实（「距上次连上 GitHub 已超过一个月」），与谁发起的检测无关，所以按来源过滤本来就没有依据。节流戳保证同一次会话里点第二次不会再弹。
    - **对话框新增「7 天内不再提醒」。** 新增 prefs 字段 `updateSnoozeUntil`（ISO 时刻），`SNOOZE_DAYS = 7` 是常量并从 store 导出，按钮文案里的数字取自同一个常量 —— 改一处即可，不会出现「按钮说 7 天、逻辑是 3 天」。天数由实现方选定（用户只说了「做一个多长时间内忽略的按钮」）。
    - **静默的边界划在对话框上，不划在状态上。** 被静默时 `updateInfo` 不设值（所以不弹框），但 `updatePhase` 仍照常变成 `available`。因此版本号右侧那行扩到了 `available`（新增键 `update.availableShort`，「有可用更新。」）—— 它是静默期间唯一的提示，也保证手动点检查更新时不会「点了没反应」。**静默提示绝不能等于隐藏更新。**
