# 层级管理器（批量移动项目与任务）

> **这一份已经与最终实现对齐：正文说的是「做成了什么」，不是「当时打算做什么」。**
> 与获批稿不同的地方就地标出，编号对应文末的《获批之后的修订》。改动有五处：四处是批准前后的修订（其中**一处是用户推翻了我的交互设计**：「锁住」→ 普通复选框树），第五处是用户在看到它跑起来之后追加的一件事。

## 背景

那个弹窗原来是「项目管理」，只能干一件事：把一个或多个**项目**并进另一个项目。而真正需要它的场合是**任务一多、在甘特图里一个个拖不现实** —— 拖拽要求落点就在屏幕上，落点在别的项目深处时你得先滚过去（拖动中不会自动滚）。

于是它变成**层级管理器**：一次勾任意多个**项目和任务**，一起送到一个落点。落点可以是**一个项目**（落在它的顶层）、**一个任务**（挂成它的子任务），或者**一个新建的项目**。

**拖拽不动。** 两者的分工是一条线：拖拽管「近且少」（落点在眼前），这个弹窗管「远或多」（落点要滚过去、或者一次几十条）。和文件管理器一样：看得见的文件夹就拖进去，看不见就用「移动到…」。还有一条更硬的边界：**这个弹窗不决定同级之间排第几** —— 一个选择器能说出「归谁」，说不出「插在这两行中间」，那是拖拽独占的事。

## 屏幕上长什么样

- 标题「层级管理器」，宽度从 520 提到 **860**。**两棵树在同一行**：左边标签「**将**」、右边「**放到**」—— 一句话的两个词。右边那棵和左边是**同一棵树**，只是单选。
- **右边那棵比左边短一档**，下面一行「**或 [创建为新项目]**」，让那个按钮的下端和左树的下端对齐。
- 中间「**项目移动方式（如涉及）**」（原「方式」），勾选里没有项目时**置灰**。
- 底下是**预览图**，再底下是折叠的**历史操作树**（复用 `history.title`，不再有「项目操作」这个名字）。
- 部分勾选画成**半格**（`input.indeterminate`）。

## 勾选：一棵普通的复选框树

三条规则，写在 `movingUnits`（`lib/tree.ts`）里：

1. **勾一个节点 = 勾它整棵子树。** 勾项目就是全选。
2. **取消一个节点 = 它所有祖先的勾一起掉**，并且**连它整棵子树一起取消**。祖先已经不"整个"走了，所以它自己那条勾必须掉。
3. **要搬的 = 勾选集合的极大元。**

「勾了项目再单独勾它里面某个任务」这种矛盾状态由第 1、2 条**根本到不了**。

这条规则放 `lib/` 不放组件，理由就是它是最容易写错的那一条，而组件里的规则 check 够不着 —— 见《获批之后的修订》第 3 条。

## 核心：`mergeInto` 泛化成 `moveInto`

```ts
moveInto(
  tasks, projects,
  units: { projects: string[]; tasks: string[] },
  target: { parentId: string | null; projectId: string },
  asFolder: boolean,
  newId: (project: Project) => string,
): { tasks; projects } | null
```

- **落点是一个「地方」，不是一个 id**。`{parentId: null, projectId}` 是项目顶层，`{parentId: taskId, projectId}` 是挂在那个任务下面 —— 这两样正好是 `placeTasks` 全部需要的，所以「落点是个任务」没多花什么。
- **一次 `placeTasks` 全落位**：`[新建的文件夹们…, 勾选的任务根…]` 一次放到 `target`；然后源项目的顶层任务 `parentId` 直接改成对应文件夹的 id（挂进的是刚建的空文件夹，没有兄弟列表要重排，那份顺序因此原样保留）。
- 原样保留的既有规矩：**先落位、后改 `projectId`**（顺序反了会把源自己的顶层行当成目标的原有行一起编号）、归档行只改 `projectId` 不重新挂父、空项目不建文件夹、重复名字不去重。
- **新增的三条拒绝**：落点是待办、落点是归档行、**落点在正在搬的东西里面**（循环）。最后一条 `placeTasks` 看不见 —— 它要落的那个文件夹是全新的，看不出和谁有血缘。
- `mergeProjects` 退化成一层薄壳，调用点和检查脚本一个字没改。

## store

`moveUnits(units, target, asFolder)`，`target` 是**三种之一**：`{kind:'project'|'task', id}` 或 `{kind:'newProject'}`。

`newProject` 在**同一个 `withUndo` 里**先 `addProject` 再落位 —— 两次 `set` 被折成**一步**历史。`addProject` 内部自己也调 `withUndo`，嵌套时外层标签胜出。

## 历史：`scope` 换成 `kind`

`HistoryStep.scope?: 'project'` 表达不了「任务移动」：它既不是项目层面，也不该被排除。换成 `kind?: 'move'`，`withUndo` 第三个参数同步改名。

**新增、改名、删除项目不带 `kind`** —— 它们不是移动，那个弹窗列的是移动。甘特图拖拽**带** `'move'`：它就是一次移动，而那段是那棵树的视图，不是另一份记录。

## 验证

1. `npm run build`（先 `tsc --noEmit`）通过；**14 个 check 全绿**。
2. `scripts/check-project-merge.mjs` 新增的断言，每一条都是这一步会**静默**错掉的方式：落点是个任务（子行挂上去、`projectId` 跟着目标走、按列出顺序排列）；项目 + 它自己的任务一起交进去时**那个任务是货物**（目标下只多一行：文件夹）；项目当文件夹和任务当自己，在同一个任务落点下并排；折进文件夹的那批**保持原顺序**（它们的 `order` 一个都没被重排）；四种循环/非法落点全部返回 null；`movingUnits` 的七种勾选状态（含「勾项目 + 勾它里面的任务结果不变」和「归档行不算单位」）。
3. `scripts/check-history.mjs`：`addProject` **不带** `kind`、`moveUnits` 和 `moveTasks` **都带** `'move'`。
4. **没有浏览器自动化**：两棵树的宽度、加宽之后的观感、预览图对不对，只能人工看。**这次不截图当证据。**

## 获批之后的修订

1. **「锁住」改成普通的复选框树。** 获批稿写的是「勾一个项目 → 它下面所有行显示为已勾并**锁住**，要单独搬某一个任务就先去掉项目的勾」。用户推翻：**不锁**，底下的勾可以取消，代价是项目那一行的勾**跟着掉**。这一条比获批稿对 —— 他描述的是复选框树的通行行为（子树、祖先、极大元），而「锁」是我把「全选」误读成了一种模式。改完之后第 1、2 条规则同时解释了「矛盾状态到不了」和「取消一个叶子等于说『除了这个都要』」。
2. **取消一个节点连它整棵子树一起取消。** 获批稿只写了「祖先的勾一起掉」。真做的时候发现只掉祖先是不够的：父节点没勾、子节点还勾着，屏幕上是「这行没勾、底下几行勾着」，而那几行确实会自己搬走 —— 没人能从那一眼里读出来。
3. **勾选的两条规则都挪进 `lib/tree.ts`。** 获批稿里这条规则是「组件里的逻辑，进不了 check，不假装验过」。写完发现按用户当天早些时候定下的规则（能算的逻辑放 lib），**那句话本身就是信号**：它不是"验不了"，是**放错了地方**。挪出来之后它成了这次断言最多的一块。
   - **而且第一次只挪了一半。** 挪走的是 `movingUnits`（读集合），留下的是「点一下集合怎么变」—— 而后者恰恰是用户推翻「锁住」时争论的那一条。补齐成 `toggleTicked`，两条规则和它们的读法一起断言：勾一个项目 = 勾它每一行、取消一个叶子 = 它和祖先的勾一起掉而兄弟留着、取消一个项目 = 整棵子树一起掉。
4. **`kind` 只留 `'move'` 一个取值**，没有照计划把 `'priority'` 一起写进联合类型 —— 一个还没有任何代码产生的取值就是留着的死灵活性，等真做批量改优先级那天再加。
5. **「创建为新项目」在只勾了一个任务时变成「升为项目」**（用户追加，不在获批稿里）。他给的类比很准：**把项目移动进另一个项目，被移动的项目自动变成父任务；那么把任务新建为项目，这个任务也应该从任务变成项目** —— 两个方向是同一件事的镜像。原来的写法会得到「新项目 → 里面一个同名任务 → 再里面才是子任务」，白花一层，而那一层要说的正是同一件事。实现是 `promoteTask`（纯函数，和 `moveInto` 并列）＋ `moveUnits` 里一个分支；**预览图必须走同一条分支**，否则那张图就是另一个操作的图。同一轮里用户还要求**三棵树都默认折起**（我原来按甘特图任务的约定做成了默认展开）。
