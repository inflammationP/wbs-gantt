# 父任务：今日待填提醒 + 批量填写子任务日志

## Context

严格任务的进度只从日志来，所以「今天欠了哪几条」是每天都要回答的问题。现在要回答它，只能逐条子任务点开看 —— 而问题恰恰出在**父任务**这个视角上：父任务就是那个把子任务汇总起来的东西，却看不出谁还没写。

这次在父任务的详情面板里补上两件事：

1. **今日待填提醒** —— 只列今天还没写日志的子任务名字。
2. **写日志时能一次填多个** —— 父任务的「写日志」按钮打开的还是那个日志编辑界面，只是多一个**待填子任务下拉菜单**，填完一条不关窗、自动跳到下一条，全部填完或按「取消」才退出。

父任务自身的日志能力不变（下拉里的第一项就是它自己）。

## 一、判定必须只有一份

这是本次唯一的正确性风险。日面板的日志环和日历格子的深浅，都由 `strictLogRate`（`src/lib/dayTasks.ts:144`）算「当天该写的严格任务」和「已写的」，它是六个条件的合取：

```
严格 ∧ 阶段 ∧ 无子任务        (isStrictLeaf)
∧ 当天在窗口内                 (activeOnDay)
∧ 当天没暂停                   (isPausedOnDay)
∧ 昨天之前没到 100%            (progressBefore < 100)
∧ 今天没写过                   (loggedOnDay)
```

如果新列表自己抄一遍这套条件，两处一定会漂：用户会看到环显示「还欠 2 条」而列表只列 1 条，或者反过来。所以**先把判定抽出来共用**：

```ts
// src/lib/dayTasks.ts
/** 当天该写日志的严格叶子，以及各自写没写。 */
export function strictLogObligations(tasks, logs, day): { task: Task; logged: boolean }[]

// strictLogRate 改为它的薄包装，行为一字不变
export function strictLogRate(tasks, logs, day): StrictLogRate
```

`strictLogRate` 的三个调用方（`CalendarPage`、`DayDetailPanel`、以及 `daySummary` 里的 `ring`）都不用改，只是底层换成新函数。

**注意最后那两个条件是有意义的**：`progressBefore < 100` 意味着**昨天之前就做完的任务不算欠** —— 列表不会去唠叨已经完成的工作；`loggedOnDay` 是「今天写过了」。

## 二、父任务面板里的提醒

`src/components/TaskDetailPanel.tsx` 新增一节，放在「写日志」按钮下面、History 上面（它是提醒，位置要显眼）。

- **只有该任务有子任务时才出现**；叶子任务照旧。
- **只列待填的**，每条只有子任务名字（没有日期、没有正文、不可点）。
- 一条不欠时显示一行 `day.allLogged`（「All strict work logged」）—— 这是查漏补缺的落点：确认没有漏的。**复用这个 key 而不是新造**，它是同一句话；`i18n.ts` 里为同一句话维护三语两份正是这个文件一直在防的事。
- 子树里一条严格任务都没有时，整节不出现（没有可欠的东西）。
- 范围是**整棵子树**（用 `collectDescendants`，与甘特图行序一致）。锚点取 `today`（store 里每 60 秒刷新的那个），跨天自动更新。

**这一节不做的事**：不允许在此写、改、删日志，名字也不可点。写日志只有一条路 —— 下面的下拉弹窗。

## 三、写日志弹窗：加一个下拉，能连着填

改 `src/components/LogDialog.tsx`。

**开启条件（推断，不加 prop）**：`!existing && hasChildren`。即「在一条有子任务的任务上新建日志」时才进入批量模式：

- `existing` 有值 → 编辑单条，行为与今天完全一致，没有下拉。
- 新建 + 叶子 → 与今天完全一致（存了就关），没有下拉。
- 新建 + 有子任务 → 批量模式。

**下拉选项** = `它在今天的待填子任务`（§1 的 `pendingLogsUnder`）。默认选中**第一个待填的**。

> **⚠️ 获批后改过 —— 见文末「八、获批之后的修订」第 1 条。** 原方案是「这任务自己 + 待填子任务」，实现后按反馈改成了只列叶子，没有缺口时不再出下拉。

**保存**：
- `addLog({ taskId: 当前选中, date, content, targetProgress })`
- 重新推一次待填列表：**还有 → 不关窗**，下拉自动前进到下一条，日期/正文/目标进度清空；**没有了 → 关窗**。
- 这条规则同时覆盖了所有情况，不需要给叶子特判：叶子永远没有待填子任务，所以「存了没待填 → 关」正好等于今天的行为。

**按钮文案**：还有下一条时显示 `log.saveNext`（「保存并继续」），最后一条显示 `common.save`。一个按钮写着「保存」却不关窗是会让人愣住的。

**表单状态要按任务重置**：`date` / `content` / `targetProgress` / `showTarget` 现在都只在挂载时取初值（`LogDialog.tsx:23-26`），而批量模式下 `taskId` 会**原地换**。把表单部分抽成一个内层组件，用 `key={currentTaskId}` 挂载 —— 换任务即换 key，状态天然重置，不需要 effect、也不会踩 `StrictMode` 双跑。同时 `isStrict`（`:40`）会跟着新任务重算。

## 六、明确不做

- **不从父任务跳到子任务**（上一版的想法作废）—— 因为这正是要避免的：跳来跳去就没法一次填多条。
- **不在父任务里渲染日志正文、不做改／删**。父任务是提醒，不是日志管理器。
- **不动 Logs 页面**（你已确认那边有「按任务筛选 = 整棵子树」）。记一笔：那一页能看、能改、能删，但**全页没有创建日志的入口**（`logDialog` 只在 `LogsPage.tsx:194` 以编辑模式被设置过）。本次不补。
- ~~**不修 `LogDialog.tsx:40` 的 `isStrict`**（它没判叶子，所以带严格标记的父任务会看到「设置目标进度」输入框，而那个值全应用没有地方读）。想修是一行 `&& !hasChildren(tasks, taskId)`，另行处理。~~ **获批后按你的要求修了** —— 见文末第 2 条。

**一处已知的副作用，需要你确认**：批量模式按「有子任务」推断，所以**在别处给父任务新建日志也会进入批量模式** —— 日详情面板的「为这天写日志」（`DayDetailPanel.tsx:173`）和甘特图右键菜单（`ContextMenu.tsx:66`）都调 `LogDialog`。行为是自洽的（那天这棵子树欠什么就列什么），但确实超出了「父任务详情页」这个范围。不想要的话就在 `Props` 上加一个 `batch?: boolean`，只由 `TaskDetailPanel` 传。

## 七、验证

1. `npm run build` —— 三语齐全由编译器兜底。
2. 清掉 `wbs-gantt.v2` 后**硬刷新**（HMR 不重跑模块级代码）。建项目 → 父任务 → 两条严格子任务，窗口都覆盖今天。
3. 选中父任务：出现「今日待填」，**只列两条子任务的名字**，没有日期和正文。
4. 核对**与日面板一致**：打开该日的日详情面板，日志环读数应与这一节列出的条数相同（同样欠 2 条）。这是 §1 抽函数的验收点。
5. 点父任务的「写日志」→ 弹窗顶部出现下拉，默认选中**第一条待填子任务**；填写 → 按钮显示「保存并继续」→ 保存后**窗口不关**，下拉跳到第二条，**日期／正文／目标进度已清空**（这是 key 重置的验收点）。
6. 填完第二条 → 窗口**自动关闭**；父任务面板的「今日待填」变成 `All strict work logged`；日面板的环同步变成满。
7. 再次点「写日志」→ **不再有下拉**（没有缺口了），弹窗直接写在这条任务自己身上；按「取消」→ 不写任何东西、关窗。
8. 选中一条**叶子**严格子任务 → 「写日志」弹窗**没有下拉**，保存即关，与改动前一致。
9. 编辑已有日志（History 行的笔）→ 没有下拉，保存即关。
10. 给一条**非严格**或**未开始**的子任务核对：它不出现在待填列表里，也不出现在下拉里（`activeOnDay` / `isStrictLeaf` 的验收点）。
11. 跨天：把系统日期往后调一天（或改 store 的 `today`）→ 待填列表跟着变。
12. 三种语言各看一遍，重点看法语下拉宽度与「保存并继续」的换行。

## 八、获批之后的修订

三处按你的反馈改的，都不在原方案里。

1. **下拉菜单只列叶子，不再有「这任务自己」。** 原方案把这条任务自己放在第一位，为的是不砍掉「在父任务上写一条随手记」。实现后你指出下拉仍然显示着更高级的任务 —— 实测确认了成因：**带严格标记的父任务本身就在第一项**，而它正是「今日待填」刚刚正确地拒绝列出的那个高级任务（`isStrictLeaf` 要求无子任务），于是看上去像「显示了所有待填任务」。现在选项来自 `pendingLogsUnder`，**与提醒逐个相同**。
   - 连带：**没有缺口时不再出下拉**，按钮退回成原来的日志按钮，写在这条任务自己身上；叶子任务、编辑已有日志两条路径完全没变。
   - 这条改动同时让「批量模式」的开启条件从「有子任务」变成「有子任务**且有缺口**」，所以原先那条「在别处给父任务新建日志也会进批量模式」的副作用也一并收窄了。
2. **`LogDialog` 的 `isStrict` 补上叶子判定**（原方案明确不做）。`strictProgress` 在带子任务的任务上是空转的（`taskProgress` 只在叶子分支被调用），所以「设置目标进度」收上去的值全应用没有地方读。现在有子任务时不显示这一栏，`submit` 也传 `null`。
3. **详情面板的「进度模式」对父任务改说「由子任务汇总」**（新增 `task.modeRolledUp`）。这是 §2 的根源：面板原本只读 `strictProgress`，于是带子任务的严格任务也显示 `Strict (log-based)`，而全应用其它地方都当这个标记不存在 —— 一条空转的标记看起来就像一条待填的任务。

**验收**：`npm run build` 通过；另用 Playwright 驱动真实应用跑了 16 项断言（父任务显示「由子任务汇总」且不再声称 log-based；提醒只列叶子；下拉与提醒一致；一趟填完两个缺口；无缺口时无下拉、无目标进度栏；严格叶子仍有该栏且日志写在叶子上），全过。
