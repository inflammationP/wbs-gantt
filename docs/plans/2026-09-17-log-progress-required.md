# 日志进度：两个格子，必填

## 背景

严格任务的日志里，「目标进度」现在是折叠起来的一个可选格（[LogDialog.tsx:205-229](src/components/LogDialog.tsx#L205-L229)）。不填，`taskProgress` 就退回「写过日志的天数 ÷ 窗口天数」自动累加（[progress.ts:34-38](src/lib/progress.ts#L34-L38)）—— 于是「今天没干」和「干了但忘了填」在数据上分不出来，进度自己往前跑。

用户要的是：今天没干，就写日志说明原因、进度填 0，而且填 0 要一步到位，不要心算「现在是 40，我该填 40 还是填 0」。

改动只有三件事：进度格拆成两个联动的格子、从折叠变常显、从可选变必填。**从界面上彻底删掉「不填进度就按天数累计」这条路** —— 从此再也写不出一篇没有进度的日志。

**本轮不动「非严格任务」这一类**（进度随日期自动涨、到期自动完成）：`autoProgress`、`strictProgress`、新建任务窗口里的勾选框全部原样保留。也不做数据迁移。

## 两个格子怎么联动

- **基准** = 这条日志**日期前一天**的进度：`taskProgress(task, 其余日志中日期 ≤ 日期−1 的那些, 日期−1) ?? 0`。排除正在编辑的这一条（否则把日期往后改时会拿自己当基准），基准日一律用 `toISO(addDays(toDate(date), -1))` 算，不要用 JS 的 `date - 1`。
- **增量格**（标签「进度增加」，带 `%`）与**结果格**（标签「进度累积至」，带 `%`）互为镜像，谁被输入谁就是主，另一个每次渲染由基准推出。改日期 = 改基准 = 非主格跟着变，主格不动。
- **底下用一行淡色小字写出基准**：`目前进度 40%`，样式同 [LogDialog.tsx:202](src/components/LogDialog.tsx#L202) 的 `text-[11px] text-dim`。没有这个数，「进度增加」没有参照；有它，日期一改结果格跳变才是可读的，否则看着像 bug。
- 两个格子都不放占位符：占位符里的 `0` 会被当成已经填好的值，而这正是本次要收紧的地方。
- **钳位只做一次，钳结果格**：`绝对 = clamp(基准 + 增量, 0, 100)`，增量再由它倒推。于是增量的合法区间是 `[-基准, 100−基准]` —— **不要把 `min={0} max={100}` 抄到增量格上**。主格在失焦时同步成钳后的值，否则「填 −80（基准 50）」会显示成 −80 而存的是 0，格子里的数和保存的结果对不上。
- **增量格必须是 `type="text" inputMode="decimal"`，不能用 `type="number"`**：number 框里打一个 `-` 会报 `value === ''`，负数根本打不进去，而负数正是这次改动存在的理由。解析要容忍「只有一个负号/小数点」= 还没打完，不是 0。
- **新建**：两格都空。输入被清空时，主格保持原样（`src` 记的是「最后动过哪个格」，不是「哪个格有值」），两格一起回到空 —— 不能只清一个，否则空格子显示着一个像样的数字，红框和屏幕对不上。
- **编辑已有日志**：结果格是主，预填该日志存的值；增量格 = 值 − 基准。两格都是填好的，用户不需要回头动任何旧日志。
- **提交**：结果格为空 → 该格标红 + 一行必填提示，不保存。按钮维持现状（只有正文为空才禁用）—— 用户要的是「跳过时告诉我」，不是「按不动」。顺带补一个 `if (!date) return`：日期格是允许清空的，清空后写进去的日志日期是 `''`，会排在所有真实日期之前、落进每一天的 `logsUpTo`，今天就已经是个隐形的坏行。

### 一个新状态位：`touched`

`{ src, input }` 之外还要记「用户到底动没动过」。原值作为种子在挂载时冻住（`useState(() => ...)`，`LogForm` 已经在用这个写法），`touched = input !== 种子`。

理由：一篇旧日志打开后**直接点保存**必须是**彻底的 no-op**。若不加判断照写 `target = 基准`，虽然读出来的数不变，但这条日志从此有了明确的进度值，会把下面那条兜底永久关掉 —— 一次什么都没改的保存改写了数据。`touched` 为假时原样写回 `existing?.targetProgress ?? null`。

## 改动清单

### 1. `src/lib/progress.ts` — 往回找，而不是只读最新一条

`:30-38` 现在只读最新一条日志：它填了目标就用它，**没填就退回按天数累计**。改成从最新往回找**第一条填了 `targetProgress` 的**（判断用 `l.targetProgress != null`，`storage.ts:202` 和 `useStore.ts:437` 都规范成 `null` 而非 `undefined`）。

这一改顺手修掉一个现有的 bug：现在一篇没填进度的日志会**抹掉**上一篇明确写的 50，把它换成「已写天数 ÷ 窗口天数」算出来的 11%。往回找之后，明确写下的值不会被后来一篇空日志推翻。

**兜底那条保留，不删。** 它现在的触发条件收窄成「这个任务一篇填过进度的日志都没有」—— 也就是只可能是本次改动之前的老数据。理由：

- 老数据一个数字都不变。删掉兜底的话，全部日志都没填过进度的严格任务会归零，**更糟的是**：窗口内写满日志因而被算成 100% 的任务，本来是「已完成、不再欠日志」的，会突然变成 0% 并**从此天天欠日志**（[dayTasks.ts:202](src/lib/dayTasks.ts#L202) 的 `progressBefore >= 100` 不再跳过它），环的分母整个跳一次。
- 保留它，入门引导里那段讲解（`guide.explain.strict.p3`，三语）**一个字都不用改** —— 它逐字写着「最新一条填了目标就以它为准；一条都没填就按已写天数 ÷ 窗口天数累计」，这句在新规则下仍然成立。FEATURES.md 第 203 行要求讲解与代码推导对得上，所以这是实打实的省。

代价要说清楚：**应用里仍然留着一条「进度可以自动长」的代码路径**，只能由老数据走到，界面上再也造不出新的。这恰恰是用户认为有欺骗性的那个机制，我选择让它留在旧数据上而不是把旧数据的数字抹掉 —— 如果你更想要「一条没填过就是 0」，说一声，那就是删掉 `:34-38` 加改三语讲解文案。

`autoProgress`（`:6`）与 `averageProgress`（`:42`）不动。

### 2. `src/components/LogDialog.tsx` — 折叠改成两个常显的必填格

- 删掉 `showTarget` 折叠开关（`:145`、`:205-229`）与 `log.setTarget` 那个按钮。
- `LogForm` 的进度状态从 `useState<number|null>` 换成上文的 `{ src, input, 种子, touched }`。
- 基准用 `useMemo` 算，依赖 `logs`、`task`、`date`、`existing?.id`。`LogForm` 现在没拿 `logs`，从父组件传下来（父组件本来就有）。基准计算留在 `LogForm` 内部；**若上提到 `LogDialog`，memo 的依赖里必须有 `logs`**，否则连续保存时会拿旧值。
- `strict` 的判定现在是手抄的（`:113`），和 `dayTasks.ts:88` 的 `isStrictLeaf` 是同一套条件 —— 把它从 `dayTasks.ts` 导出、这里复用。一个必填格写在「没人读这个值」的任务上，是这类重复里最糟的一种。
- 红框用 `border-delayed`（`delayed` 是 tailwind 色板里现成的信号色，`text-delayed` 是全应用现成的红，见 [UpdateOverlays.tsx:98](src/components/UpdateOverlays.tsx#L98)）。不给 `Field` 加 error 属性 —— 一个字段不值得开这个口子。
- 批量模式不用改：`LogForm` 已按目标任务 id 做 key（`:104`），换任务即重置，每个任务各自从空开始、各自的基准。注意 `pendingLogsUnder` 出来的每一条都是严格叶子，所以批量几篇就是几个必填格 —— 这正是预期。

## 一个行为变化

往回找之后，一篇没填进度的日志**不再推翻**之前明确写下的值。老数据的可见数字全部不变，唯一变的是这个：以前「先标 100% 完成、之后再随手写一篇不带进度的日志」会把任务退回未完成，现在它会停在 100%。新日志一律带进度，所以这条只会影响老数据。

2. `node scripts/check-day-obligations.mjs` —— 含上面新增的三条。
3. `npm run dev` 手动过一遍：
   - 严格叶子写日志：两格常显；空着点保存 → 结果格变红出提示、不保存；填增量 → 结果格自动算出；填结果 → 增量格自动算出。
   - **在增量格里打负数**（打 `-`、再打数字），确认负号不被吞掉。

   - 把日志日期往后改 → 底下那行「目前进度」变、非主格跟着变、主格不动。
   - 同一天再写一篇 → 基准是上一篇的结果值。
   - 打开一篇旧日志 → 两格预填好；**什么都不改直接保存 → 进度、数据均不变**。
   - 在带子任务的父任务上点批量写日志 → 逐条切换时两格各自从空开始，每条独立填。

## 获批之后的修订

用户见到实现后改了三处，都不在获批的方案里：

1. **报错时两个格子一起标红**（原方案只标结果格）。
2. **必填提示要指明是哪个格子** ——「没进展就在「进度增加」里填 0」。笼统的「填 0」有歧义：往结果格里填 0 是把进度清零，意思正好相反。
3. **推翻「增量可为负」。** 获批方案里写着增量允许负数，理由是「把一个高值写回 0 就是这么写的」；用户改为**进度不能往回填** —— 结果格低于当天开始时的进度就报错。这条只查用户真正填过的值，否则旧数据里那些回落过的记录会被自己的保存挡住。
